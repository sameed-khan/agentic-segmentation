# GUI-Actor-2B and Molmo2-8B as MRI pointer specialists

**Research checked:** 2026-05-18. Primary-source-first; no weights downloaded, packages installed, or code run. Inline citations link to the source supporting the adjacent claim. Estimates/inferences are labeled.

## 15-line summary
1. GUI-Actor-2B is Qwen2-VL-2B plus a learned visual action/pointer head; it returns normalized candidate point(s), not ordinary text coordinates.
2. It is the better first low-risk deploy on one A10: BF16 weights are roughly 4–5 GB by model class, before runtime overhead.
3. Its official input preprocessing allows max_pixels=5,720,064; patch=14 and merge=2, so a 1000×1000 panel fits without exceeding the configured cap.
4. The actor head's patch attention is converted by official code into connected, thresholded regions and weighted patch-center points.
5. GUI-Actor-Verifier-2B is a separate Qwen2-VL judge: red-circle candidate screenshot + instruction → True/False / probability; it is optional, not the actor.
6. Official GUI-Actor inference is repo-local Transformers code; pin Transformers 4.51.3 and qwen-vl-utils 0.0.8, not a generic text-serving endpoint.
7. Molmo2-8B combines Qwen3-8B (36 layers) with SigLIP 2 So400m/14 (27 layers, 378px crops) and a learned pooling/MLP connector.
8. Molmo2 emits textual `<points coords="…">` spans; point coordinates are 0–1000-normalized x/y with IDs, not calibrated confidence scores.
9. Molmo2 supports single-image pointing, multiple points/counting, multiple images and video, but no verified exact `k` constraint or ranked candidate API.
10. Molmo2 card's default `dtype="auto"` is a trap for this GPU: released checkpoint weights are FP32 (~34.7 GB estimated); Ai2 says explicit BF16 loading is safe.
11. BF16 Molmo2 weights are ~17.3 GB estimated, plus image/KV/runtime memory; tight on a nominal 24-GB A10 and not reliable alongside nnInteractive's 1–5 GB.
12. For Molmo2 concurrent use, test BitsAndBytes 8-bit/NF4 (est. ~8.7/~4.3 GB weights) or serialize GPU work; quantized vision/code compatibility and quality are not guaranteed by Ai2.
13. Upstream llama.cpp supports Qwen2-VL multimodal/projector, but has no verified GUI-Actor pointer-head route; plain Qwen2-VL Q4_K_M is not GUI-Actor pointer inference.
14. Molmo2 is officially supported by vLLM >=0.15 per Ai2 repo; no official Molmo2 upstream llama.cpp conversion found. GUI-Actor vLLM/SGLang cards do not establish custom-head point outputs.
15. MRI domain gap is the main scientific risk: evaluate all 169 slices paired, raw/no-mark and mark conditions, top-k/point-in-GT, nearest-mark accuracy, latency and bootstrap CIs against 82.6%/70.4% baselines.

## Findings

### GUI-Actor-2B (Microsoft)

**Architecture / image path.** The model card identifies the backbone as `Qwen2-VL-2B-Instruct`, augmented with an attention-based action head and fine-tuned on GUI-Actor data ([official HF card](https://huggingface.co/microsoft/GUI-Actor-2B-Qwen2-VL)). Its config declares `Qwen2VLForConditionalGenerationWithPointer`, Qwen2-VL text hidden size 1536, 28 layers, 12 attention heads, 2 KV heads, and vision spatial patch size 14 ([raw config](https://huggingface.co/microsoft/GUI-Actor-2B-Qwen2-VL/resolve/main/config.json)). Processor config: `patch_size=14`, `merge_size=2`, `min_pixels=3136`, `max_pixels=5720064` ([raw processor config](https://huggingface.co/microsoft/GUI-Actor-2B-Qwen2-VL/resolve/main/preprocessor_config.json)). Thus its effective spatial unit is 28×28 input pixels; 1000×1000 is below the configured maximum. Qwen2-VL dynamically resizes within min/max pixel limits; there is no fixed single input resolution here. **Not verified:** exact count/shape of all vision-tower parameters from this actor checkpoint's config.

**How locations are produced.** The paper describes a dedicated `<ACTOR>` token and attention-based action head that attends to relevant visual patches and can produce multiple regions in one pass ([NeurIPS paper page](https://proceedings.neurips.cc/paper_files/paper/2025/hash/16130af940e9dabb43c726119bd3b42e-Abstract-Conference.html); [paper PDF](https://proceedings.neurips.cc/paper_files/paper/2025/file/16130af940e9dabb43c726119bd3b42e-Paper-Conference.pdf)). In the released implementation, the concrete token sequence includes `<|pointer_start|>`, `<|pointer_pad|>`, `<|pointer_end|>`; the hidden state at pointer-pad is passed with image embeddings to `multi_patch_pointer_head`. That head computes patch relevance with projected query/key dot products and softmax ([official modeling.py](https://raw.githubusercontent.com/microsoft/GUI-Actor/main/src/gui_actor/modeling.py); [inference.py](https://raw.githubusercontent.com/microsoft/GUI-Actor/main/src/gui_actor/inference.py)). The inference helper thresholds patch scores at 0.3×maximum, finds 4-neighbor connected components, scores each by mean activation, and returns score-weighted patch-center coordinates normalized to width/height (0–1). `topk` means top connected regions, not top individual patches; `topk_points_all` retains their constituent normalized patch centers. `topk_values` are raw region activations, not calibrated probabilities. The official helper returns `attn_scores`, grid dimensions, candidate centers, scores and all points; it does not return a bbox/heatmap image by default.

**Verifier.** `microsoft/GUI-Actor-Verifier-2B` is a distinct model based on UI-TARS-2B-SFT. It judges an instruction plus screenshot with a red circle at a candidate point, outputs True/False, and can use label probability to score; it is trained using OS-Atlas-derived positive/negative UI examples ([official verifier README](https://raw.githubusercontent.com/microsoft/GUI-Actor/main/verifier/README.md); [HF card/example](https://huggingface.co/microsoft/GUI-Actor-Verifier-2B)). Use only to rerank GUI-Actor candidates in a separately reported arm; its GUI-trained point judgment is not validated for MRI.

**Exact inference stack.** Official project setup: Python 3.10 (repo permits >=3.10,<3.13), clone `microsoft/GUI-Actor`, `pip install -e .`; pyproject pins `transformers==4.51.3`, `qwen-vl-utils==0.0.8`, `accelerate==1.1.1`, `flash-attn==2.7.3`, `liger-kernel==0.5.2` (plus Pillow, datasets etc.) ([official pyproject](https://raw.githubusercontent.com/microsoft/GUI-Actor/main/pyproject.toml); [README](https://github.com/microsoft/GUI-Actor)). `inference.py` imports repo `gui_actor.modeling`, `gui_actor.constants`, and `qwen_vl_utils.process_vision_info`; use that local checkout/editable install, not generic `AutoModel` for actor output. Official snippet loads `Qwen2VLProcessor`, custom `Qwen2VLForConditionalGenerationWithPointer.from_pretrained(... torch_dtype=torch.bfloat16, device_map="cuda:0", attn_implementation="flash_attention_2").eval()` then `inference(conversation, model, tokenizer, processor, use_placeholder=True, topk=3)`. Prompt is a system instruction (“You are a GUI agent…”) and user content with image followed by instruction text. The helper injects the pointer/action placeholder into its custom chat template. Model card's generic `trust_remote_code` / vLLM examples show ordinary image-text use and do **not** demonstrate extraction of pointer scores. Config metadata says Transformers 4.47.1 whereas official repo pins 4.51.3: follow the repo's explicit tested dependency pin; versions are not interchangeable without validation.

**License/data/failure modes.** Code repository declares MIT ([LICENSE](https://github.com/microsoft/GUI-Actor/blob/main/LICENSE)); model is a fine-tuned Qwen2-VL derivative, so review upstream Qwen2-VL model license and card terms as well. Actor finetuning data is GUI grounding data ([card and linked dataset](https://huggingface.co/datasets/cckevinn/GUI-Actor-Data)); no medical/radiology training data was identified in the cited actor sources. Verifier data is OS-Atlas GUI. Expected risk/inference: patch-level granularity, threshold/connected-component dependence, and GUI-specific semantics may miss diffuse/low-contrast MRI lesions; labels such as “fibrous soft-tissue tumor” may be outside UI-target concepts. The code's spatial scores are rankings, not calibrated confidence.

**Benchmarks.** Official repo reports Qwen2-VL GUI-Actor-2B: ScreenSpot-Pro 36.7, ScreenSpot 86.5, ScreenSpot-v2 88.6; with verifier: 41.8, 86.9, 89.3 respectively ([official result table](https://github.com/microsoft/GUI-Actor#main-results)). These are GUI benchmarks and not predictive of MRI localization. Results are source-reported; not independently rerun here.

### Molmo2-8B (Allen Institute for AI)

**Architecture / image path.** HF card says Qwen3-8B language backbone + SigLIP 2 So400m/14 vision backbone ([official card](https://huggingface.co/allenai/Molmo2-8B)). Config identifies `Molmo2ForConditionalGeneration`, a 36-layer text model (hidden 4096, 32 heads/8 KV heads), vision hidden 1152, 27 layers, 378×378 input and 14px patch size; connector takes ViT layers -3/-9 ([raw config](https://huggingface.co/allenai/Molmo2-8B/resolve/main/config.json)). Report's table gives ~8.2B LLM + 380M ViT + 88M connector (sum ~8.67B, **researcher arithmetic**, not a stated exact total). The report says one downscaled crop plus up to 24 overlapping crops for inference; crops are resized to 378 even if aspect ratio changes, and images not tileable within K are downscaled. 2×2 patch-window pooling followed by shared MLP connector. Therefore high-res is tiled, not arbitrary continuous ViT resolution. **No absolute max-pixels setting was verified**; crop cap is the relevant documented constraint ([technical report §3](https://arxiv.org/html/2601.10611)).

**Point format / extraction.** Molmo2 is autoregressive: prompt with ordinary language such as “Point to the [target]”; output may include a `<points coords="…">` structured span. Official model-card parser for video/multi-image reads integer point IDs and x/y values, assumes x/y on 0–1000 scale, then multiplies by image width/height and divides by 1000; it handles multiple point records, frame/image indices, and `<points>`/`<tracks>` tags ([HF card code](https://huggingface.co/allenai/Molmo2-8B)). The paper describes normalized x,y, image index or video timestamp, and distinct integer IDs for objects to enable counting/tracking; multiple points are supported, with video training examples up to 60 annotated points ([report §3](https://arxiv.org/html/2601.10611)). For one image, parse the points tag to pixels with `x_px=x_norm/1000*W`, `y_px=y_norm/1000*H`; use point emission order as rank only. No native scalar score, guaranteed sorting by confidence, or supported request-time `k` control was verified. The exact single-image tag grammar is less completely documented than the video/multi-image parser; validate parser against actual output before serving.

**Exact inference stack.** Official HF card quickstart specifies Python 3.11 and `transformers==4.57.1`, then `torch pillow einops torchvision accelerate decord2 molmo_utils`; loads `AutoModelForImageTextToText` and `AutoProcessor` with `trust_remote_code=True`, `dtype="auto"`, `device_map="auto"`; messages are role/content entries with `{type:"text", text:...}` and `{type:"image", image: PIL.Image}`. `processor.apply_chat_template(messages, tokenize=True, add_generation_prompt=True, return_tensors="pt", return_dict=True)` then `model.generate(...)` ([official card](https://huggingface.co/allenai/Molmo2-8B)). Ai2 repository documents HF inference and Molmo utilities, and states vLLM support >=0.15.0 ([official repo README](https://github.com/allenai/molmo2#transformers-and-vllm)). For image-only PNG use that HF chat-template path; `molmo_utils.process_vision_info` is shown for video and can be omitted for the simple single-image snippet. Use a point prompt, not “describe”.

**Important FP32 / memory finding.** The HF config says `dtype: float32`; Ai2 confirms released weights were kept FP32 but explicitly says loading in BF16 was tested with negligible output differences under SDPA ([Ai2 response](https://huggingface.co/allenai/Molmo2-8B/discussions/7)). Therefore the card's `dtype="auto"` is not an A10-safe promise and may load FP32. **Estimates:** ~8.67B × 4 bytes ≈34.7 GB FP32 (does not fit); BF16 ≈17.3 GB; 8-bit ≈8.7 GB; NF4 ≈4.3 GB, excluding quantization scales/overheads and any unquantized modules. Text KV cache at 36 layers × 8 KV heads × 128 dim × K/V × 2 bytes ≈144 KiB/token; with ~25 crops and ~196 pooled tokens/crop ≈4,900 visual tokens, cache is about 0.7 GB, plus generated text and prompt, temporary vision tensors, CUDA/runtime allocations. This is a **back-of-envelope** estimate; actual crop count, GPU allocator, dtype, activation and backend change use. Explicit BF16 weight load is plausible solo but tight against 21GB free; sharing with nnInteractive using 1–5GB likely requires quantization or sequential GPU scheduling. Ai2 does not publish these deployment VRAM numbers or a single-image latency in the cited sources.

**Quantization and serving compatibility.** HF Transformers supports BitsAndBytes 8-bit/4-bit configuration ([official quantization docs](https://huggingface.co/docs/transformers/quantization/bitsandbytes)); compatibility of the full Molmo2 vision+connector custom remote model and output fidelity at NF4/8-bit is **not verified by Ai2**. Treat as an experiment, keep output parser and fixed benchmark tests. AWQ/GPTQ for either custom pointer system: no official compatible quantized checkpoint/workflow verified. Molmo2 official vLLM path is documented starting 0.15.0; use HF Transformers first for pointer parsing and establish point-output parity before vLLM. SGLang support for these custom pointer outputs: **unverified**.

`llama.cpp` upstream multimodal docs enumerate Qwen2-VL and offer Qwen2-VL GGUF + `mmproj`, but do not list Molmo2; no official Molmo2-8B GGUF/model conversion was found ([upstream multimodal docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md)). Community search found a Molmo2-4B conversion dependent on a non-upstream fork, not verified Molmo2-8B support. GUI-Actor's underlying Qwen2-VL vision may be supported in llama.cpp, but its checkpoint declares a custom `...WithPointer` architecture and requires the trained Python pointer head + patch embeddings. A generic Qwen2-VL Q4_K_M conversion does not preserve/execute that head. Thus **Q4_K_M via upstream llama.cpp is suitable only for supported vanilla Qwen2-VL, not the verified GUI-Actor pointer task; Molmo2-8B Q4_K_M pointer inference is not verified/officially supported.** A GGUF text response alone is not evidence of image projector and pointer functionality.

**License/data/failure modes.** HF card says Apache-2.0, but explicitly warns its training third-party datasets are subject to academic/non-commercial research use; inspect dataset terms before use ([model card](https://huggingface.co/allenai/Molmo2-8B)). Image pretraining includes PixMo-Points/PixMo-Count/CoSyn-Point; SFT includes image/video pointing, natural-image QA/captioning, tracking and Tulu NLP data; report says data constructed without proprietary-model distillation. No MRI/clinical medical data identified in the published dataset summary ([report](https://arxiv.org/html/2601.10611)). Risk/inference: natural image/video-object concepts may not transfer to axial MRI histotypes; a language model can produce plausible but inaccurate points; normalized outputs can be malformed/out-of-bounds or multiple points can describe examples rather than single lesion.

**Benchmarks.** Image pointing: Molmo2-8B Point-Bench average accuracy 68.7 (subscores affordance 84.8, spatial 71.3, reasoning 71.5, steerability 44.5, counting 71.4) in the technical report; Ai2 later reports PixMo-Points F1 85.2 ([report](https://arxiv.org/html/2601.10611), [Ai2 comparison](https://allenai.org/blog/molmopoint)). Image counting: report Table 6 has CountBench/PixMoCount image benchmarks; the precise scores were not reliably extracted here and are **unverified in this brief**. RefCOCO: no Molmo2-8B result located in official report/card; **no result verified**. Reported video grounding (not comparable to single-slice MRI): Molmo2-8B video counting accuracy 35.5 and video-pointing F1 38.4 on paper's respective evaluations ([report](https://arxiv.org/html/2601.10611)).

## Local deployment recommendation

**Recommended implementation:** Python 3.11 `uv` virtual environment per model to avoid incompatible Transformers pins; install a CUDA 12.8-compatible PyTorch build separately per official PyTorch selector. Do not try to keep both stacks/processes loaded concurrently on the A10. Start with GUI-Actor 2B BF16 as a custom Transformers inference worker (repo checkout editable, `transformers==4.51.3`, `qwen-vl-utils==0.0.8`, `accelerate==1.1.1`, Pillow, FastAPI/Uvicorn); use its returned `topk_points`, `topk_values`, `attn_scores`, grid dimensions. Separately test Molmo2 with `transformers==4.57.1`, `trust_remote_code=True`, explicit `torch_dtype=torch.bfloat16` (or `dtype=torch.bfloat16`, supported spelling depends on installed Transformers), SDPA, single image, small `max_new_tokens`. If a concurrent nnInteractive reservation is mandatory, try BitsAndBytes 8-bit first, then NF4; monitor actual reserved/allocated VRAM and evaluate all 169 cases before choosing quantization. Use GPU process/model unload or a single serialized GPU queue. No latency claim is available from sources.

A minimal wrapper contract (implementation sketch, not tested):

```python
# POST /point
# request: {"image_png_base64": "...", "query": "the fibrous soft-tissue tumor", "k": 3,
#           "model": "gui-actor" | "molmo2", "marks": false}
# response: {"points": [{"x": 431.2, "y": 289.4, "score": 0.31}],
#            "latency_ms": 123.4, "raw_output": "...", "coordinate_space": "pixels"}
```

Decode base64 to RGB PNG and preserve original width/height. For GUI-Actor multiply normalized returned x/y by original W/H; include region score, rank, raw attention/grid in optional diagnostics. For Molmo2 parse `<points>` IDs and normalized coordinates into pixels; assign `score: null` (or rank-only metadata), do not fabricate confidence. Cap output to `k` but retain raw output; `k` does not control Molmo2's generation internally. Reject malformed/out-of-range points; record preprocessing, load-time vs request latency and model revision. Do not return clinical advice.

## 169-case evaluation protocol

1. Freeze the 169 same rendered single-slice PNGs and GT lesion masks/points used in frontier-model comparison; freeze histotype queries and preprocessing/model revisions. Use identical query text and original image dimensions.
2. Evaluate each model on raw PNG + histotype, no marks as primary condition. Repeat with numbered set-of-marks labels as separate condition. Do not mix training/prompt development with held-out reporting.
3. GUI-Actor: log top-1 and top-k connected-region centers, raw patch scores/grid, component scores; optionally test verifier reranking as its own ablation. Molmo2: log first emitted point and all points/IDs; treat order as rank, not confidence.
4. Primary metrics: lesion hit rate (point lies inside GT mask), point-to-GT distance in pixels and normalized by image diagonal, and top-k any-hit. For set-of-marks compare both direct nearest-mark snap (Euclidean pixel distance, predeclared tie-break) and mark-ID exact/GT-hit; do not score a snapped point as the model's raw point.
5. Compare paired accuracy to frontier set-of-marks 82.6% and raw coordinate 70.4% on identical cases; report absolute percentage-point differences and case-paired bootstrap 95% CIs, plus per-histotype/subgroup breakdown only when adequate n. Report malformed/no-point rate, number of emitted points and latency distribution (median/p95) on the actual server.
6. Inspect misses for MRI/UI visual-domain gap, lesion size/contrast, ambiguity, slice context absence, and text phrasing sensitivity. Prompt ablation should compare concise noun phrase (“Point to the fibrous soft-tissue tumor”) with a neutral full instruction; avoid adding clinical explanatory details that could leak labels.

## Contradictions, gaps, and risks

- **Transformers versions:** GUI repo dependencies pin 4.51.3; actor config metadata says 4.47.1. Molmo2 card prescribes 4.57.1 and config says 4.57.1. Use model-specific environments, not a single global install.
- **Memory:** Molmo2 card's `dtype="auto"` conflicts with practical A10 fit because config/checkpoint is FP32; Ai2 explicitly confirms FP32 checkpoint and safe BF16 loading. BF16 is estimated to fit only with little headroom; exact peak VRAM and concurrency were not published or measured.
- **Serving/quantization:** upstream llama.cpp supports vanilla Qwen2-VL multimodal, but no evidence that its Q4_K_M path keeps GUI-Actor custom head. Molmo2-8B upstream llama.cpp support/GGUF and custom point decoding remain unverified. Generic vLLM/SGLang card launch examples do not prove pointer-score export.
- **Medical transfer:** Neither cited model has verified MRI-specific training or prospective clinical validation. GUI-Actor's direct training domain is interfaces; Molmo2's published data is general images/videos and related public datasets. Expect prompt- and mark-overlay sensitivity and do not substitute output for radiologist review.
- **Latency:** No official single-image A10 latency report located for these exact checkpoints; report measured per-request latency and cold-start separately in the study.
- **Molmo2 score gaps:** exact Molmo2-8B CountBench/PixMoCount table values and any RefCOCO score are not asserted here; RefCOCO result was not found.
